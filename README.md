intl-ai translates your locale files with any AI provider, at build time or on demand. One Rust binary, no Node dependency, no runtime code. A lockfile tracks per-key provenance and review state, so AI output never silently overwrites human work.

![intl-ai demo](docs/public/demo.gif)

## Why intl-ai

Most i18n translation workflows are manual (copy JSON, open a translation tool, paste back) or runtime-heavy (call an AI API on every page load). intl-ai runs at build time so translations are baked in before your app ships.

- **Zero runtime overhead.** Translations happen during the build, not in the browser or on the server.
- **Any stack.** The binary reads and writes `locale_dir/{locale}.json|yaml` files, so it pairs with i18next, next-intl, vue-i18n, react-intl, Paraglide, and anything else that consumes flat locale files.
- **Any AI provider.** An OpenAI-compatible HTTP endpoint, or a local agent CLI (`claude-code`, `opencode`, `codex`, `crush`, `gemini`) for keyless dev.
- **Lockfile-tracked origins.** `intl-ai.lock.d/` records whether each translation was written by a human or generated by AI, plus a review bit, so you always know what to trust.
- **Additive by default.** `fill` writes missing keys only. Existing values (human or AI) are never touched unless you pass `--stale`, `--regenerate`, or `--include-human`.
- **Shift-left validation.** `fill --validate` re-prompts the provider with check feedback until output is ICU-clean; `check` fails CI on missing, stale, or invalid translations.

## Quick start

```bash
intl-ai init          # writes intl-ai.toml + a replay cassette
# edit intl-ai.toml: set locale_dir, source, targets, provider
intl-ai fill          # translate missing keys
intl-ai check         # audit: missing, stale, invalid, unreviewed
```

A minimal config:

```toml
locale_dir = "locales"
source = "en"
targets = ["fr", "de"]

[provider]
kind = "http"
model = "your-model"
api_key = "${env:OPENAI_API_KEY}"
```

Or go keyless with a local agent CLI:

```toml
[provider]
kind = "command"
agent = "claude-code"
```

## Commands

| Command                                  | What it does                                                          |
| ---------------------------------------- | --------------------------------------------------------------------- |
| `intl-ai init`                           | Scaffold `intl-ai.toml` and a replay cassette                         |
| `intl-ai fill`                           | Translate missing keys (additive by default)                          |
| `intl-ai check`                          | Read-only audit: missing, stale, invalid, modified, extra, unreviewed |
| `intl-ai status`                         | Per-locale inventory counts                                           |
| `intl-ai mark <keys> --origin ai\|human` | Set key provenance (or `--absent` for tombstones)                     |
| `intl-ai review` / `unreview`            | Set or clear the review bit on keys                                   |
| `intl-ai lockfile check\|fmt\|merge`     | Validate, normalize, or merge lockfile shards                         |
| `intl-ai config validate\|schema`        | Validate a config file or emit the JSON Schema                        |
| `intl-ai migrate`                        | Import a 0.4.x `intl-ai.lock.json` into shards                        |

Every command accepts `--format json` for agent and CI consumption.

## Configuration

intl-ai reads `intl-ai.toml`, `intl-ai.json`, `intl-ai.yaml`, or `intl-ai.yml`, discovered by walking ancestors to the `.git` boundary. Override with `--config PATH` or `--config -` (TOML on stdin).

- Provider kinds: `http` (OpenAI-compatible chat completions), `command` (local agent CLI preset or free-form command), `replay` (deterministic cassette for tests).
- `${env:VAR}` and `${file:PATH}` interpolation, `extends` for shared base config, `INTL_AI_*` env overlay.
- `intl-ai config validate` checks a config file; `intl-ai config schema` emits the JSON Schema (also on [SchemaStore](https://intl-ai.pages.dev/schema/v1.json)) for editor autocomplete.

See [Configuration](https://intl-ai.pages.dev/guide/configuration) for the full schema.

## Lockfile and review workflow

`intl-ai.lock.d/<locale>.toml` holds one sorted TOML block per key: source hash, written value, `origin` (`ai` or `human`), and `reviewed`. Commit it — it is a text format designed for git diffs and merges (`intl-ai lockfile merge` resolves conflicts union-style, human wins).

- A value that differs from what AI last wrote counts as human-owned: `fill` will not touch it, and a stale source marks it as a `check` finding, never an auto-rewrite.
- `intl-ai review` / `unreview` manage the review bit; `check --fail-on unreviewed` is the human-in-the-loop gate for CI.

## CI

`intl-ai check --fail-on missing,stale,invalid` exits 10 when findings fire and prints a JSON report under `--format json`. Run it after `fill` (or standalone) in your pipeline.

## Migration

Coming from the deprecated `@intl-ai/*` npm packages:

1. Install the binary (see Install above); drop the `@intl-ai/*` dev dependencies.
2. Rename `intl-ai.config.ts` / `.json` to `intl-ai.toml` (config keys are now snake_case: `api_key`, `locale_dir`, `source`/`targets` instead of `defaultLocale`/`locales`).
3. Run `intl-ai migrate` in your project to import the old `intl-ai.lock.json` into `intl-ai.lock.d/` shards.
4. `--force` is gone: use `fill --stale` (AI-owned stale keys) or `fill --regenerate` (all AI-owned keys); `--include-human` additionally covers human-owned values.

The TypeScript implementation is frozen on the [`legacy` branch](https://github.com/sigilco/intl-ai/tree/legacy); the scoped packages remain on npm with a deprecation notice for pinned installs.
